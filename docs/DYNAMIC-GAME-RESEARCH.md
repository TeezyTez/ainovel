# 聊天中的动态游戏界面：一手资料核验与架构建议

核验日期：2026-10-10。范围：Friends & Fables、Chub Stages、RisuAI、Infinite Worlds，共 6 个官方页面。此次阅读官方文档、示例和更新说明，没有登录试玩，也没有测量实际可靠性；“官方描述的机制”与“本项目建议”分别陈述。没有依据宣传页推断其完整内部架构。

## 结论

建议采用“公开场景状态 → 当前可做的行动 → 聊天内的临时交互组件 → 校验后的结果 → 新状态”的闭环。游戏感来自可操作对象、条件、后果和后续反馈；地图、背包或进度条本身不会产生玩法。组件应由当前场景需要产生，结束后留下可回顾的结果，不把每一类游戏信息做成永久面板。

“不写死”应理解为不写死某个世界的地点、人物、数值和操作内容；仍需要少量可靠的界面原语、行动协议和状态规则。让模型每轮生成任意 HTML/JavaScript，会把规则验证、存档和历史回溯都变成不稳定问题。

## 官方机制与证据边界

### Friends & Fables：位置和物品参与实际场景

官方 ACE-1.5 更新说明描述了 POI 局部地图：玩家以自然语言移动，拾取和放下物品会对应地图与背包变化；NPC 距离影响参与对话的人物和注入的角色背景。官方同时承认，按地图图片颜色等视觉描述移动尚不准确。手机地图是可隐藏的浮窗，并非本文建议的聊天内组件。可借鉴其“空间改变可互动对象”的机制，不能据此承诺其定位或库存每次都正确。[来源 1：ACE-1.5](https://fables.gg/patch-notes/ace-15-bringing-pois-and-npcs-to-life-npc-conversations)

### Chub Stages：消息生命周期和界面生命周期分开

Stage 是小型 React 应用，有初始化、请求前、响应后、切换历史节点时的回调；`render` 可随时执行。Stage 还能附加仅人类可见的系统消息，与送给模型的正文分开存储。其默认可见区域是桌面侧栏或手机顶部，`NONE` 可完全隐藏；不能把它描述成已经验证的任意聊天内布局系统。值得借鉴的是事件钩子和独立呈现层，而不是照搬固定侧栏。[来源 2：Stage Concepts](https://docs.chub.ai/docs/stages/developing-a-stage/concepts)

状态分为 initialization、message、chat 三类。初始化状态可保存一次生成的地图；人物血量、当前位置、走过的路径属于跟随消息分支的 message state；chat state 是跨分支共有的特殊状态，官方以保留探索迷雾的知识为例。这直接说明重试、回退和另开分支时，游戏位置与资源不能共用一个全局可变对象。[来源 3：Stage State](https://docs.chub.ai/docs/stages/developing-a-stage/state)

### RisuAI：显示变换、按钮事件、持久变量

官方 Lua 文档提供输入、输出、发送时的回调，按钮能调用指定函数；`listenEdit("editDisplay", …)` 可以按状态改变显示。`setState/getState` 保存 JSON 可序列化数据，聊天变量保存字符串。脚本每次触发重新执行，局部变量不能充当跨轮记忆。显示回调的能力有限，说明呈现与执行不宜混在一起。该文档不能证明其现版所有界面行为或自动历史回滚正确，本文仅采用文档明确给出的 API 机制。[来源 4：Trigger Script — Lua Mode](https://kwaroran.github.io/docs/srp/lua/)

### Infinite Worlds：受约束的状态操作

PawScript 将表达式和修改状态的脚本区分开来。世界作者定义 tracked items，形状可以是数值、文字或结构化数据；人物、库存和任务不必都预先塞进固定 RPG 数值表。这是“可扩展数据模型”的参考，不能据此推断产品支持任意自定义地图或动态 GUI。[来源 5：PawScript Reference](https://infiniteworlds.app/pawscript-reference)

脚本由 trigger effect 执行，只能修改 tracked items，不能直接显示消息或调用 AI。条件和有限循环可实现消耗、治疗、任务阶段变化；官方明确说明脚本出错时整次变更不生效。可借鉴受限变更协议与原子提交，而无需为本项目立即引入新脚本语言。[来源 6：Writing Scripts](https://infiniteworlds.app/pawscript-script-guide)

## 对当前代码的判断

本地查看 `src/experience-state.js`、`src/experience-views.js`、`src/experience-controls.js` 及叙事架构文档：项目已具备有稳定 ID 的公开对象、正文原句证据、历史快照、分支/状态版本检查，以及原子提交方向。现有情况查询主要放在集中面板里，适合回顾，但不能独自承担“眼前就能操作”的游戏循环。

保留 `publicSituation` 作为公开信息边界，复用现有物品、人物、地点 ID。增加薄的交互协议与聊天内渲染层；不另建一份与现有 inventory、location、experience 对象各自漂移的“游戏真相”。

## 推荐契约（本项目设计推论，并非上述产品的共同实现）

1. **场景**：保存 `sceneId`、当前公开地点、相关对象 ID、已知通路、待处理局面。只使用玩家已经获知的信息，缺少路线证据时不画假地图。
2. **可行动项**：使用 `{id, verb, targetIds, label, preconditions, sourceVersion, branchId}`。例如查看封条、把钥匙交给某人、尝试沿已知路线移动。模型可提出行动项，宿主验证对象存在、可见性和版本；不能用文案伪装已经成功。
3. **组件**：采用 `{id, sceneId, kind, objectIds, actionIds, status, anchorTurnId}`。`kind` 是受支持的布局原语，不是具体剧情类型；内容来自当前场景。
4. **执行**：按钮和自然语言最终走同一个行动入口。先验证行动意图与当前状态，再生成/判断后果，最后把正文、事件、游戏状态、组件结果一起提交。失败或取消不扣物品、不移动、不留下成功结果。
5. **回执**：交互结果展示确实发生的变化，如“钥匙已交给林澈”“北门仍锁着”。下一轮规划读取已提交结果，避免按钮完成后故事对此失忆。

既有 `quote` 只能证明某段文字确实出现过，不能证明数值合法或行动合理。结构化资源需要类型、单位、范围和守恒/消耗规则；依靠正文包含一句话不够。尚无数值依据时显示“负伤”“体力不足”等公开状态，不临时编造 73/100。

## 条件界面的生命周期

| 阶段 | 触发 | 在聊天中如何表现 | 状态要求 |
| --- | --- | --- | --- |
| 产生 | 当前局面确有空间、对象或待处理动作 | 在相关叙述旁出现局部界面 | 有来源、对象 ID 与场景 ID |
| 活跃 | 条件仍成立且位于当前分支末端 | 显示少量当前可做的操作 | 每次点击重验版本和条件 |
| 处理中 | 行动请求已发出 | 就地显示动作与等待反馈 | 禁止重复提交，保留取消路径 |
| 已解决 | 动作完成或局面结束 | 收为结果条，可展开回顾 | 保留回执与发生时快照 |
| 已离场 | 换场、目标离开、物品耗尽 | 不再占用当前操作区 | 历史仍可查看，动作失效 |
| 回看历史 | 用户查看旧消息或其他分支 | 展示当时组件的只读快照 | 不拿当前库存覆盖旧图 |

组件隐藏不等于删除状态；解决一个局面也不等于从历史中移除其结果。默认仅当前尚待处理的场景组件可操作。返回旧分支末端时应从该分支恢复状态并重新验证行动，而不是复用旧 DOM 按钮。

## 首批值得做的三种原语

| 原语 | 何时出现 | 有意义的操作 | 何时收起 |
| --- | --- | --- | --- |
| 局部路线图 | 出现明确空间选择 | 选择已知目的地/查看路线条件；提交移动意图 | 抵达或离开该场景 |
| 对象操作区 | 得到、发现或需要一个物件 | 查看已知细节、尝试使用、交给当前人物 | 已使用、已交付、情境结束 |
| 局面处理区 | 谈判、制作、调查或冲突有具体可决策步骤 | 选对象、工具、目标，看到约束与结果 | 问题解决或玩家离开 |

人物状态/任务变化可作为这些组件内的简短反馈。不要默认给所有故事添加血条、等级、货币或任务清单。地图首版用拓扑节点与关系即可；不知道距离时不放比例尺，不知道道路时不自动连边。线索关联也应使用有类型的关系，不能把任意 `relatedIds` 当作空间相邻。

## 防止“好看的卡片”替代玩法

- 只有标题、图片和“继续”按钮：只是展示。至少需要目标、当前限制、可选方法和可以被下一轮读取的变化。
- 按钮只往输入框塞句子：可作为草稿帮助，但应明确属于建议；真实交互需要目标 ID、分支/版本和可追踪回执。
- 每轮都重画全量背包/人物/地图：信息负担会随故事增长。只呈现当前改变决策的部分，完整记录按需查阅。
- 显示层重新渲染时扣资源：必须禁止。渲染只读，状态操作只在受控提交阶段发生。
- AI 自己宣告“钥匙消失”而库存未变：提交时检测正文与事件对应的实体，至少验证持有和数量规则；不能承诺单纯字符串匹配解决语义一致性。
- 按钮暗示结果确定：未知结果使用“尝试”或明确条件。查看已有记录不推进时间，故事内调查/移动则作为真实行动提交。

## 最小验收场景

进入分岔路时出现仅含已知路线的地图 → 选择工坊并抵达 → 地图收为到达回执 → 发现封存匣后出现对象操作 → 选择使用已有钥匙 → 校验持有后开匣并记录物品变化 → 对象操作收为结果 → 后续人物能够引用开匣结果。

必须同时检查：重复点击只执行一次；取消生成不改状态；旧回合按钮不能消耗当前物品；分支 A 的开匣不影响分支 B；未经发现的地点不出现在地图；刷新后恢复相同状态；不选择按钮也可以自然语言行动。无适用玩法的安静对话应允许只显示聊天，而不是强制生成面板。
