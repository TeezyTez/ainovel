# 智能交互与 ChatGPT 聊天端的差距调查

调查日期：2026-10-14。用户要求先调查，本轮未修改应用代码、提示词、模型配置或玩家存档，也未发起新的真实模型生成。

## 结论

当前差距涉及交互架构，不能归结为原生 JavaScript 不如 React。

- **触发少**主要有已复现的路由、失败缓存和面板生命周期问题，再叠加保守的模型判断与生成等待。
- **效果不好**存在明确的表达上限：模型只能填写固定的数据协议，不能创造新的控件行为、布局算法或可运行交互程序。现有渲染器也存在布局与局部更新缺口。
- **模型运行条件**可能进一步影响质量：本机公开状态接口返回 `Codex 本机授权 / gpt-6-sol`；调用固定为低推理强度、单次结构化输出，没有工具、技能或截图检查。其影响需要对照实验，不能仅凭设置断言是主因。
- **官方对照的边界**：ChatGPT 的公开交互能力可以核实，但没有用户具体对照会话，无法确认用户看到的是哪条实现路径，也不知道内置功能的完整技术栈。

## 1. 对比的是哪一种能力

暂按“聊天中自动出现、可以直接操作的小界面”理解。官方 Visualizations 展示参数调整、动画与逐步演示，并支持后续对话修改。这是可观察的产品能力，不是内置实现说明。[官方 Visualizations](https://learn.chatgpt.com/docs/visualizations)

公开的 MCP Apps UI 则提供 iframe 内运行的界面、工具调用和模型上下文回传。它是可参考的第三方集成机制，**不能据此认定内置 Visualizations 就使用同一套实现**。[官方 UI 开发说明](https://developers.openai.com/plugins/build/chatgpt-ui)

本项目当前机制：

```text
剧情提交 / 进入场景
  → 后台请求 prepare
  → 同一次模型输出决定是否需要界面，并生成完整 JSON
  → 结构校验 + 世界一致性审核
  → 保存单个 dynamic 定义
  → 固定渲染器生成表格 / 图卡 / 表单
```

它比较接近“模型填写的结构化辅助面板”。与可以按问题编写新交互的产品之间，存在任务设计、输出协议和运行能力的差距。

## 2. 触发少：已经找到的实际路径

### 2.1 普通表达没有进入智能交互

对当前真实导出函数运行了纯本地路由探针，按 `sendTurn` 中的顺序检查生成交互、本地查询及普通意图识别：

| 输入 | 实际入口 |
| --- | --- |
| 用表格比较北路和南路 | 生成智能交互 |
| 展示人物关系图 | 生成智能交互 |
| 比较北路和南路 | 本地资料比较，要求名称对应已登记对象 |
| 帮我比较一下这几条路线 | 剧情行动 |
| 画个路线图 | 剧情行动 |
| 给我做个可以拖动的物资分配面板 | 剧情行动 |
| 把这个改成时间线 | 剧情行动 |
| 把这个图放大一点 | 剧情行动 |
| 这个关系图加上刚才的船员 | 剧情行动 |

这不是模型能力测试：这些句子在到达界面生成模型之前，已经被正则路由分流。后续剧情更新仍可能再次自动判断界面，因此“走剧情行动”不等于永远不能显示，但它已经丢失了只整理或修改现有界面的意图。

证据：[app.js:167、184–199](../src/app.js)、[rich-request.js:2–12](../src/rich-request.js)、[interaction-context.js:4–29](../src/interaction-context.js)。

### 2.2 生成失败被当成可复用结果

前一轮隔离复现已经确认：注入 `INVALID_MODEL_RESULT` 后，服务端保存 `definition:null` 和错误原因；同场景再次自动请求直接复用失败，模型调用总数仍为 1。客户端也将该场景加入 `attempted`，没有定义时渲染为空。

真实账本中，“山门之外”开场存在这一错误代码，区别于模型主动认为无需界面。该代码覆盖多种无效输出原因，当前记录不足以继续细分解析失败、截断或 CLI 异常。

证据：[server-dynamic.mjs:32、49–59](../src/server-dynamic.mjs)、[dynamic-ui.js:53、74、87–88](../src/dynamic-ui.js)、[server-model.mjs:140–160](../src/server-model.mjs)。

### 2.3 “保留已有界面”没有独立语义

上下文把旧定义直接作为 `pending` 发送。模型可以回答“现有界面已承载比较，无需新界面”，但服务端收到 `needed:false` 就清空定义。

“生化危机：灰港封锁”的保存理由正是这一情况；隔离旧版本面板也复现了相同路径。当前只有“新定义 / 无需界面”，缺少“保留 / 更新 / 关闭 / 失败”之间的明确区分。不能简单地对所有 `needed:false` 保留旧图，因为已过期内容本来就应隐藏。

证据：[server-dynamic.mjs:14、38、49–59](../src/server-dynamic.mjs)。

### 2.4 判断保守，且界面生成要经过串行审核

提示词要求只有确实受益时才生成，差异不足宁可不生成。准备调用同时承担用途判断、组件选择、内容组织、表达式和动作规则生成；没有单独的轻量交互规划阶段。成功定义还要等待第二次模型审核，审核重点是真实性和规则一致性，没有对视觉效果进行检查。

本地 9 个非“验收”标题存档中，共读到 17 次 prepare、6 次 judge 的已保存耗时：

| 阶段 | 最小 | 中位数 | 最大 |
| --- | ---: | ---: | ---: |
| prepare | 8.614 秒 | 13.040 秒 | 20.083 秒 |
| judge | 8.368 秒 | 10.618 秒 | 13.883 秒 |

这只是历史存档样本，不是当前性能基准，两个阶段的中位数也不能当作端到端中位数。一个已完成的自动路线验收用时为 28.484 秒。用户继续输入时，客户端会取消尚未完成的 prepare；这提供了“结果尚未出现就被下一轮取消”的可能路径，但现有日志没有取消次数，不能判断其实际占比。

证据：[server-dynamic-model.mjs:5–10、29–40](../src/server-dynamic-model.mjs)、[server-dynamic.mjs:35–47](../src/server-dynamic.mjs)、[app.js:170](../src/app.js)、[自动验收记录](../test-results/rich-live-2026-10-13T02-41-58.652Z/manifest.json)。

## 3. 效果不好：协议限制比 CSS 更关键

### 3.1 输出格式限制了可生成的交互

| 能力 | 本项目实际支持 | 对体验的影响 |
| --- | --- | --- |
| 丰富视图 | table、chart、diagram、cards、timeline、illustration 六类 | 新用途只能组合这些类型 |
| 图表 | 固定横向条形图，最多 12 项 | 无通用折线、多系列或图表刷选协议 |
| 关系图 | flow / radial；最多 12 节点、24 边 | 布局和关系探索方式不能由模型定制 |
| 输入 | number、text、choice、multiple、boolean | 无原生滑块、拖放分配或图上编辑控件 |
| 插画 | 最多 80 个受限 SVG 图元 | 无任意 HTML、脚本、外部图片、动画或图元事件 |
| 表格 / 图卡操作 | 排序、筛选、放大、折叠、写入草稿 | 主要是查阅与准备输入，缺少跨视图探索 |
| 数值联动 | 有限表达式、条件与计算预览 | 能做确定规则表单，但不是通用交互程序 |

这些是本项目主动限定的协议范围，并非浏览器或原生 JavaScript 的能力上限。也不能说当前“完全没有交互”：已有排序、筛选、数量预览、多步骤输入和正式动作提交。

证据：[rich-interaction.js:1–65](../src/rich-interaction.js)、[dynamic-rules.js:47–79](../src/dynamic-rules.js)、[dynamic-ui.js:20–30、96–103](../src/dynamic-ui.js)、[rich-interaction-controls.js](../src/rich-interaction-controls.js)。

### 3.2 渲染器存在确定的质量缺口

- 关系图 flow 按输入顺序排成三列，radial 把第一个节点固定居中，不根据图的语义或碰撞情况求解布局。
- 图内节点名称超过 11 字会缩略，图中关系标签超过 16 字也缩略。完整文本可以在附录查看，因此不是数据丢失，但会削弱图本身的可读性。
- 合成探针中，同一对节点的两条不同关系通过校验后，标签落在相同坐标，存在重叠。
- 合成探针中，400×240 插画画布允许坐标为 1500、1500 的图元通过校验，结构合法不保证图元在画布内可见。
- 输入改变时，只替换 `data-dynamic-values`，没有同步替换依赖该输入的字段和步骤区域；条件结构不能可靠地即时更新。

固定布局与文字缩略来自当前源码；重边重叠和画布外图元来自允许的合成输入，不声称它们已经出现在用户某次实际生成中。条件更新缺口通过实际事件回调的 DOM 桩探针复现，不是浏览器实测。

证据：[rich-interaction-view.js:42–89](../src/rich-interaction-view.js)、[rich-interaction.js:50–65](../src/rich-interaction.js)、[dynamic-ui.js:99](../src/dynamic-ui.js)。

### 3.3 一个真实成品说明了当前倾向

“雾港隔离夜”保存过名为“通往二楼前：回应门内的人”的定义：只有“医院后门外 / 门内有人 / 通往二楼的楼梯间”三个节点、两条连线，一个节点可写入对话草稿，没有输入字段或执行动作。这份定义目前已落后于故事一回合，不应作为当前有效面板展示。

它能整理已知关系，却没有增加多少玩家可操作的能力。结合协议范围，可以判断当前机制更容易产出“将正文重新排成图”，而不是围绕任务设计新的操作方式。这个判断来自具体样本和协议分析，不代表所有生成结果。

## 4. 连续对话与模型运行条件

交互生成上下文包含开场、最近三轮正文与已提交输入、当前公开状态、人物和物件，以及旧界面定义；没有直接包含完整辅助问答历史、界面修改历史或当前选中的图表对象。旧事实可能仍在公开状态中，不能把它描述成“只记得三轮故事”。

表格的排序、筛选及各视图的折叠状态主要保存在客户端 `presentations` 中，不进入 `prepare` 上下文。`pending` 虽然传递旧定义，但没有稳定的“这个图 / 当前选中对象 / 本轮修改要求”事件模型。加上前述路由，连续说“改成时间线”“只看这两个人”很难形成自然的迭代体验。

证据：[server-dynamic.mjs:14](../src/server-dynamic.mjs)、[dynamic-ui.js:33–47、89](../src/dynamic-ui.js)、[rich-interaction-controls.js:57–88](../src/rich-interaction-controls.js)。

2026-10-14 的本地 `/api/config` 返回 `available:true, provider:Codex 本机授权, model:gpt-6-sol`。当前 Codex 调用设置为 `model_reasoning_effort="low"`，忽略用户配置、临时会话、禁用宿主技能发现以及工具和图像查看，只返回符合外层 schema 的 JSON。

界面定义实际装在字符串 `payload` 中，再由应用解析和校验；外层结构化输出约束不等于内层完整界面 schema 已由解码器保证。另一条兼容 API 路径是 `json_object`、`stream:false`；本次实际运行的是 Codex 路径，不能用 API 路径的 token 上限解释当前 Codex 失败。

证据：[server-codex.mjs:8、31–47](../src/server-codex.mjs)、[server-dynamic-model.mjs:4、38–40](../src/server-dynamic-model.mjs)、[server-model.mjs:140–160](../src/server-model.mjs)。

**推断：**低推理强度和没有渲染反馈，可能不利于复杂布局与交互设计。但换模型或提高推理强度，仍不能突破 DSL 禁止的控件和行为。本轮没有进行模型 A/B，不能量化这部分影响，也不能假定用户 ChatGPT 使用相同模型和设置。

## 5. 应怎样判断技术栈方向

官方 MCP UI 快速入门直接用单文件 HTML/CSS/JavaScript 实现交互，React 只是可选工程方式。因此没有证据支持“必须整体迁移 React 才能做好”。[官方快速入门](https://developers.openai.com/plugins/build/app-quickstart)

| 方向 | 能解决什么 | 仍解决不了什么 | 判断 |
| --- | --- | --- | --- |
| 只调触发提示词、增加输出频率 | 改变模型选择倾向 | 路由、失败缓存、协议表达上限 | 不足以解决问题 |
| 修复现有链路并扩展可信组件 | 稳定业务操作、条件联动、图表和布局质量 | 每类新交互仍要扩展协议/组件 | 适合交易、资源与规则操作 |
| 增加隔离的生成式交互层 | 按场景生成探索、推演和可视解释 | 需要运行检查、状态桥接和失败恢复 | 最接近本次希望的能力方向 |
| 整体换 React / 引入 ChatKit | 改善组件开发或聊天基础设施 | 不自动补齐任务理解和生成交互能力 | 不是当前应先做的决策 |

**建议采用两层能力，而不是废弃已有账本：**

1. 可信组件继续负责真实资源、购买、移动和已审核动作。
2. 另设可运行 HTML/CSS/JS 的隔离展示层，承担只读探索、参数试算、关系浏览和临时方案；控件只通过受限事件桥接请求宿主动作，不能直接改故事状态。
3. 让模型能识别和修改已有界面，接收有用的选择状态；正式结果仍由服务端校验和提交。
4. 为生成界面增加渲染检查与修复反馈，而不只校验 JSON 合法性。

这是一项架构建议，并不是 ChatGPT 内部实现的复刻。iframe 隔离、来源限制和宿主桥接必须实际设计，不能把任意生成脚本直接放进主页面。[MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)

## 6. 下一步如何验证，避免再靠感觉调整

在实现大改前，先建立同一组标注上下文，包含：隐含比较需求、明确界面请求、修改现有图、带条件的物资准备、应保持纯文字的普通阅读。保留真实措辞，不能全部写成“现在需要比较，请整理”。

分别记录：

- 入口是否识别为界面任务；是否被误当成剧情行动。
- 判定结果是创建、更新、保留、关闭、无需、错误还是取消。
- 生成、审核、渲染各阶段成功情况与耗时。
- 控件能否完成指定任务，条件区域是否同步更新，是否修改了不应修改的故事状态。
- 标签可读性、遮挡、移动端可用性和后续对话修改能力。

比较技术方案时固定模型和推理强度；比较推理强度时固定方案和上下文。将“触发更多”与“出现了有用且可操作的界面”分开评分。

已有真实自动验收只覆盖路线比较和安静阅读，记录对应 v5，而当前为 v6。它能证明特定旧场景可用，不能证明当前日常游玩触发率或接近 ChatGPT 的交互质量。本轮渲染/控制相关测试 43/43 通过；这些测试覆盖结构与既定操作，不是内容设计质量评分。
