# 将审稿反馈交给实际负责状态的阶段

本次是已授权的叙事核心问题修复，依据真实 NAR-009 S07 的封存失败。实施前的设计与验证边界；不代表模型质量通过。

## 问题与取舍

093747 冻结运行的两次 extract 请求完全相同；具体的角色知情越界和记忆引用问题只送给输出五个草稿字段的 revise。正文没有变化，状态抽取却拿不到被拒候选或意见。只增加提示或重复相同请求不能修复这种职责错配。

采用显式状态修复路由。仅在所有问题都属于候选状态时冻结正文并修状态；正文、混合或未确定的问题继续修订正文，但后续抽取也必须收到被拒状态和意见。不通过自由文本错误码猜测类型，不增加分类模型调用、修复预算或容量上限。

## 内部接口与状态机

- review / repair_review 输出 `repair_scope`，取值为 `none`、`candidate_state`、`draft`、`mixed`、`undetermined`。批准必须为 `none`，拒绝不能为 `none`。旧录制缺字段时保守走原正文路径；显式未知类型或自相矛盾值拒绝。新模型 schema 要求此字段。类型是审稿模型的判断，不是语义真值。
- `candidate_state` 拒绝进入新阶段 `repair_state`，输入 `{context, candidate, issues}`，完整候选只出现一次，内含冻结五字段。输出沿用状态变化对象，由程序补回冻结的 title/passage/story_time/outcome/suggestions，然后独立 review。不能在状态修复中改正文制造证据。
- 其他拒绝进入原 revise → extract → review。第二次 extract 增加 `repair_feedback: {candidate_state, issues}`；candidate_state 是被拒候选删去五个草稿字段后的完整状态对象，current draft 才是本次采用正文。首次 extract 不携带该字段。
- 新阶段、正文修订、结构修复、引用修复共用原 `max_repairs <= 1`。修复后仍被拒即失败；没有 room 容纳修复及独立审稿时不启动无效修复。
- Rust 产生阶段请求、验证结构及冻结正文；Go 独立核实顺序、拒绝类型、完整候选与意见绑定、当前草稿、正式版本与来源、最终预算。候选和反馈都不是正式事实。
- repair_state 按候选目标取材，旧事实和人物身份仍由 Go 正式快照提供。混合路径取材可考虑旧候选对象，但不能把未提交的变更注入 authority 或 actor。
- 请求继续按实际 UTF-8 字节计算；24 KiB 候选上限并不保证候选、2 KiB 意见与输出 schema 的最大组合都能进入原 36 KiB 阶段预留。超限明确失败，不发起这次模型调用，不截断候选或意见、不扩大预留。常规候选的可达正控与最大组合的拒绝负控分别记录。

## 记忆引用语义

替换原有说明，不堆叠互相冲突的提示。摘要可依据本页及有效旧来源；当前 quote 支持本次新增或改变的含义和必要条件、否定、认知归属。累计摘要不要求当前 quote 重述全部旧历史。context 可以解释指代，未执行计划不能补充事件证据。正文有据、摘录不足时应修记忆状态；不能称事件虚构，也不能用整页 hash 或字符串包含冒充语义支持。

## 验证与执行次序

1. 先保存能在真实流水线接口重现缺反馈的失败测试，再实现 Rust 路由、Go 镜像和绑定。两端分工，不改正在运行的独立快照。
2. 固定输入验证状态修复保留五字段、意见/候选不可替换、混合反馈可达、预算共用、再次拒绝不提交、结构/引用修复不能追加语义重试、source/pin/read/actor 边界及真实最终容量。
3. 独立审查两端一致性，运行定向和必要回归。合成测试仅证明工程行为。
4. 当前三例真实原题自然封口后，再冻结整合源码进行真实验证；旧失败、原题、评分保持不变。真实模型是否正确修状态、保留合法的部分知情，以及人物与长程故事质量，必须由实际请求、结果和提交证据判断。
