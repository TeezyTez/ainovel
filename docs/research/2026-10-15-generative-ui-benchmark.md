# 生成式界面同题验收集

版本：2026-10-15。状态：**待执行的验收方案，不是测试结果**。目标是比较本游戏、ChatGPT 网页、Claude 网页在同题生成、连续修改、等待和恢复方面的实际体验，并单独验收本游戏的账本约束。

历史依据：[差距评估](../AI-INTERACTION-GAP-2026-10-15.md)、[真实模型验收脚本](../../scripts/verify-interactive-artifacts.mjs)。历史的 44.5 秒、81.9 秒是旧代码的一次观测，不能作为当前基准或 p50/p95；旧脚本中的 `quantity=4` 是注入的协议夹具，不等于玩家连续操作。本方案的状态必须通过界面实际操作产生。本轮只制定方案，不调用外部模型。

## 执行约定

- **C01–C16：三产品同题。** 比较公开设定的展示、试算、编辑和恢复；不要求 ChatGPT/Claude 具有本游戏账本。**G17–G20：仅本游戏。** 正式提交、撤销、幂等、分支隔离不纳入跨产品排名。
- 每个案例、每个产品至少 **5 次独立重复**：新会话/新的合成存档、无前题历史。一个连续修改链算一次重复，链内点击或三次修改不能算三个独立样本。完整最低规模为 240 次跨产品案例运行，加 20 次游戏专属案例运行。
- 使用下面的原文设定和提示，不追加产品专属提示词。游戏从正常玩家入口输入，网页从普通聊天入口输入；不绕过自然触发规则强制调用界面生成。设定放入公开开场/聊天上下文，不加入隐含事实、私有记忆或联网资料。只用临时合成存档。
- 默认桌面视口 1000×900 CSS px、缩放 100%；C13 使用 390×844。相同设备、浏览器、语言和网络。每个“案例×重复轮”作为一组，三产品在相近时段交错运行；用预先固定的随机顺序，保存顺序表和种子，不先跑完某产品再换产品。产品或模型中途更新则另开版本组。
- 每次重复保存原始提示、响应、实际操作视频、首份/最终界面截图、失败断言和时间戳。状态证据记录字段含义及数值；不以“看起来保留了”替代操作记录。
- 每一步限时 180 秒，超时记失败及 `>180s`，不删除或把它记成恰好 180 秒的成功；失败、超时均留在成功率分母，取消独列并说明是否补跑。失败后最多一次统一修复请求：`请修复以下问题：{逐字列出失败断言}。保留已有有效数据和输入；不要增加设定外事实。` 正常的预定修改不算修复；记录自动修复与人工重试，网页内部不可见的修复次数填“未知”。

## 三段共享公开设定

每题使用指定的一段设定；除明确列出的前置操作外，不沿用其他题的产物。

**A｜路线**

> 撤离前，你把三份公开路线说明铺在桌上。东桥路线是守桥人今早亲口说的：桥面还在维修，能否通行要等他回复。山径路线是你刚才亲眼看见的：入口干燥，深处坡道尚未探查。河岸路线是两天前的一封旧信写的：当时有船接应，现在船是否还在并不知道。三条路都有缺少确认的条件，当前没有哪条路线被保证安全，也没有确定的通行耗时、距离或成功概率。同行的阿青在场。你暂时没有选择或出发。

**B｜干粮**

> 你在避雨处清点出12份干粮，尚未分配。同行的是你、阿青和老陈，三人都在场；没有人已经领取干粮，也没有确定的个人配额。可以先做假设试算，但真正分发还需单独提出行动。当前没有其他干粮来源，也没有已知的每人消耗率。

**C｜安静阅读**

> 雨声落在屋檐上。你安静地读着旧书，窗外的树影缓缓摇动。此刻没有需要决定、比较、整理或操作的事项，只需继续安静阅读。

## 指标、记录与判定

时间从用户点击发送到事件实际发生，使用同一屏幕录制或单调时钟。预先完成设定加载；前置建表/建界面的耗时单列。连续链逐次记录请求耗时，链的模型等待总和与人工操作时间分列，不能让操作者思考速度污染生成延迟。

| 指标 | 统一定义 |
| --- | --- |
| 首次反馈 `t_feedback` | 发送到本次请求的可辨认受理、进度、内容或错误反馈；记录反馈类型。固定的页面装饰不是反馈，进度提示也不是可用界面。 |
| 首个可用界面 `t_usable` | 最早可正确完成该题核心检查的界面出现时刻；交互题必须实际完成一次规定操作。纯文字/不触发题填 N/A，另记首个可用文字时刻。 |
| 最终可用 `t_final` | 本次请求最后交付版本通过该步全部断言的时刻；修复耗时从原请求起继续计，不重置。失败或超时保留失败状态。 |
| 首次成功 | 首次提交、无需用户修复/重试，首个交付版本通过全部断言；连续链须所有预定步骤通过。产品内部候选是否一次通过只作本游戏诊断列，网页不可见时记未知，不能混为同一指标。 |
| 修复后成功 | 首次失败后，在上述一次修复额度内通过；同时保留首次失败、修复原因、次数及额外等待。不能回填为首次成功。 |
| 状态保留 | 每个应保留字段记录“修改前值/含义 → 修改后值/含义”，按检查点给出通过数/总数，并报告整条链是否全通过；不只检查总和。 |
| 稳定性 | 逐题记录超时、运行异常、错误触发、漏触发、假数据、状态丢失、重复成品、取消/中断及恢复结果。主动取消和账号限流独列，不静默剔除。 |

分别报告每产品、每题、每个步骤的 `n`、成功数和 p50/p95，不把不同难度题的耗时混成一个排名。p50 使用中位数；p95 使用排序后的第 `ceil(0.95×n)` 个值。只有5次时 p95 实际就是最大观测值，明确标为粗略描述，不能声称尾延迟已稳定；需要稳健尾延迟结论再增加重复。失败占比与成功条件下的延迟必须同时展示；超时使总体分位数无法确定时写 `>180s/不可估`。C16 的人为断网5秒及恢复后等待单列，不并入正常网络生成速度。

推荐单条记录：

```text
run_id, product, account_tier, model_label, build_or_hash, started_at, network,
case_id, repeat_id, step_id, prompt_version, viewport,
t_feedback_ms, feedback_type, t_usable_ms, t_final_ms,
first_success, repair_success, repair_count, internal_repair_count_or_unknown,
state_before, state_after, assertions_passed, assertions_failed,
timeout_or_error, capability_unavailable, evidence_paths
```

### 人工质量盲评

两名评审独立看同题同轮的匿名截图与操作录像：遮去品牌、账号、模型名，随机排列 A/B/C；保留实际任务内容、缺陷与交互过程。无法遮蔽的现场操作另标“未盲”，不声称完全双盲。先判硬断言，再按下表给 0/1/2 级及一句证据；分歧复核原始记录。等待速度由计时单独判断，不从界面美观推断模型能力。

| 维度 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 信息组织 | 关键信息缺失或易混淆 | 信息齐全，需来回查找 | 来源、未知、结论区分明确，能直接完成题目 |
| 可读性 | 标签、单位或核心内容不可读/被遮挡 | 可读但层级或排版影响查找 | 核心值醒目，桌面与指定窄屏均清楚 |
| 操作理解 | 控件用途或结果无法理解 | 需要试错才能完成 | 标签、反馈与约束清楚，无额外讲解即可操作 |
| 修改连续性 | 丢失有效输入或破坏核心任务 | 状态正确，但修改后需重新寻找操作 | 指定修改到位，输入、对应关系与操作路径保持清楚 |

不把四项任意加权成“达到 ChatGPT/Claude 的某个百分比”。报告逐题硬断言、四项等级、同题偏好及具体理由；展示失败案例，不能只挑最好截图。编造数值、误执行对白、丢失关键状态或错误扣账是独立失败，不能靠美观评分抵消。

**计划验收门槛：**先完成每题至少5次的完整证据；硬断言目标为每题5/5、连续链完整通过，游戏专属题零错误结算或跨分支污染。这是待验证的目标，并非已有成绩。基线采集开始前冻结题目、断言、180秒限时、修复额度和统计口径；速度先按预先定义的分位数与同题差值报告。若需要数字化响应预算，在独立试跑阶段确定并冻结后再收正式样本，不看完结果再改门槛；改协议则另起版本重跑。在拿到三产品真实同题记录之前，不发布“已全面对齐”或综合优劣排名。
