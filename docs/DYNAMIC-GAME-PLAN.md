# 按场景出现的可玩聊天

用户要求：丰富玩法在 chat 中按需出现；不写死每个世界的血条、地图和物品，不做支付和社区。本文是本轮实施计划与进度记录。

## 决策

使用受约束的生成式 UI：模型选择组件、创造世界内对象与有依据的规则；代码负责呈现、数值运算、版本校验和原子提交。借鉴 F&F 的地图/物品联动、Chub 的消息状态和 A2UI 的可信组件目录，不引入任意模型脚本。

游戏状态跟随回合与分支保存。每轮组件描述替换当轮可操作界面，实体资料增量保留。过去消息成为只读记录；查看不消耗时间，实际操作进入生成与提交。没有相关玩法时保持纯正文。旧故事下一轮即可获得组件，不迁移或覆写原文。

实体通用类型：meter/item/place/clue/objective/actor。界面目录：status/map/inventory/clues/objectives/interaction。交易、制作、战斗选择、谈判等通过交互组件与世界自定义动作组合，无按题材名称分支。确定的消耗/获得由代码运算，未确定结果以尝试交给叙事，绝不伪造概率。

## 工作分工和验收

- [x] 游戏状态/动作协议：严格验证、正文证据、旧按钮、数值上下限、成本、存档回放和分支测试。
- [x] 消息内 UI：六类布局、状态进度、路线连接、物品数量、目标进展与动作后果预览；移动端与主题适配；无组件时不占位。
- [x] 模型与应用集成：沿用两次调用和本机授权，加入组件生成与动作结算约束；增量更新旧卡片；查看与执行分离。
- [x] 独立审查 + 全量测试 + 本机真实模型的生成/点击/状态变化闭环 + 浏览器检查。证据与边界见 DYNAMIC-GAME-VERIFICATION.md。

接口分工：状态代理修改 game-state/core 和对应测试；UI 代理修改 game-ui/reading-ui 和样式测试；主代理修改 server-model/server-narrative/app 与集成验证。共享 game-state API 先明确后接线。研究代理仅写研究文档。

Ruling: 在现有工作目录实现。当前仓库无可用基线提交，用户要求直接改现有可运行原型；不创建空基线 worktree，不改变其个人存档。

Ruling: 首版提供安全声明式确定性动作与叙事尝试，不执行模型生成的 JavaScript/Lua，不凭空添加通用战斗掷骰系统。

Ruling: 场景动作完成不自动结束整局故事，按钮回合强制保留后续阅读入口。整局结束使用原有结束路径。

Ruling: 规划候选可以剔除无效的附加引用，但每个候选必须保留至少一个准确的原文依据；全无依据仍拒绝，不把转述当作原文。
